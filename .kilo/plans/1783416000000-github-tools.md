> **Scope note (item #13 clarified):** "Create new role to review pull request" means a new
> **system prompt** added to the existing `components/prompt` package — a PR-reviewer persona
> analogous to `troubleshoot.md` / `architecture.md` — **NOT** a tool. It instructs the agent

## 0. Decision — MCP vs. native Go tools

**Recommendation: build native eino tools in this repo. Do NOT delegate to an MCP server for the eino path.** Keep MCP only as a documented alternative for MCP-host consumers.

Rationale (research-backed):

- The **official GitHub MCP server** (`github/github-mcp-server`) is real, Go, actively
  maintained, and covers issues/PRs/repos/branches/releases/search. **But** it is an
  external process (Docker/remote HTTP/local binary) and its "create branch" only creates
  a **remote git ref via the REST API** — it cannot `git clone` to a temp folder or create
  a **local** working-tree branch.
- The user's very first requirement — *"clone project on temporary folder, path set when
  creating tools"* — plus *"create new branch"* implies **real local git operations**. The
  GitHub REST API (and therefore every GitHub MCP server) cannot do this. Local git
  requires `go-git/go-git`. This alone rules out a pure-MCP solution.
- eino-ext's design (AGENTS.md / CONTRIBUTING.md) mandates **self-contained Go components**
  with `Config`+`validate`+`jsonschema`, table-driven tests with **no live external service**,
  enforced **security controls** (SSRF, path traversal, secret redaction, timeouts). These
  are far easier to enforce in-process than by trusting an opaque external server.
- eino-ext already has an MCP client path (`cloudwego/eino-ext components/tool/mcp` +
  `mark3labs/mcp-go`). We will **mention** it in the README as an alternative for users who
  run an MCP-capable host, but native tools are the primary deliverable.

**Libraries to add** to `go.mod`:

- `github.com/google/go-github/v<latest>` — GitHub REST API (issues, PRs, releases, repos,
  webhooks, search, org repos). BSD-3.
- `github.com/go-git/go-git/v5` (or v6 if stable) — pure-Go clone / branch / local worktree.
- `github.com/migueleliasweb/go-github-mock` (test-only) — mock GitHub API server for tests.

> Confirm exact major versions at implementation time; pin the latest stable.

## 3. Config design (`config.go`)

Multi-instance map keyed by name (matches argocd `Configs`):

```go
// Configs maps a named GitHub instance to its configuration.
type Configs map[string]Config

type Config struct {
    // Token is the GitHub PAT or App token. Required. REDACT in all output/logs.
    Token string `validate:"required" jsonschema:"description=GitHub token (PAT or App installation token)"`

    // BaseURL for GitHub Enterprise Server. Empty = github.com.
    BaseURL string `validate:"omitempty,url" jsonschema:"description=GitHub Enterprise base URL (empty for github.com)"`

    // UploadURL for GHES uploads (releases assets). Empty = derive from BaseURL.
    UploadURL string `validate:"omitempty,url" jsonschema:"description=GHES upload URL"`

    // CloneDir is the temp folder root where repos are cloned. Set at tool creation
    // time, NOT chosen by the LLM. Required for clone/branch tools.
    CloneDir string `validate:"required,dirpath" jsonschema:"description=Base directory for local clones"`

    // Timeout for API calls. Defaulted; validated as gte=1s.
    Timeout time.Duration `validate:"omitempty,gte=1000000000" jsonschema:"description=Per-request timeout"`
}

func (c Configs) GetConfig(name string) Config       { return c[name] }
func (c Configs) GetInstanceNames() []string          { return toolutil.SortedKeys(c) }
```

Key points enforcing the repo rules:

- `CloneDir` (the "path set when creating tools") lives in **Config**, so the LLM can never
  pick an arbitrary filesystem path — prevents path traversal. Each clone goes into a
  sanitized subdir under `CloneDir` (validated: no `..`, no absolute escape).
- `Timeout` receives a default (e.g. 30s) → validated with `omitempty,gte=...`, never
  `required` on a defaulted field (per CONTRIBUTING.md).
- `validate.Struct` is called **after** defaults, inside `NewClient` / `newBaseTool`.

## 4. Client + base (`client.go`, `base.go`)

```go
// client.go
func NewClient(cfg Config) (*github.Client, error) {
    if cfg.Timeout == 0 { cfg.Timeout = 30 * time.Second }
    if err := validate.Struct(&cfg); err != nil {
        return nil, err // self-wrapped
    }
    httpClient := &http.Client{Timeout: cfg.Timeout}
    gh := github.NewClient(httpClient).WithAuthToken(cfg.Token)
    if cfg.BaseURL != "" {
        var err error
        gh, err = gh.WithEnterpriseURLs(cfg.BaseURL, orDefault(cfg.UploadURL, cfg.BaseURL))
        if err != nil { return nil, errors.Wrap(err, "invalid GHES URLs") }
    }
    return gh, nil
}

func BuildClients(cfgs Configs) (map[string]*githubClient, error) { /* per-instance, wrap errors */ }
```

`base.go` — a `baseTool` embedded by every tool, holding per-instance API clients + the
resolved `CloneDir` + known instance names, plus `client(instance)` returning a
`toolutil.NotFoundError` when unknown. `validateParams` = `validate.Struct`.

The git side (`go-git`) is small: a helper `cloneRepo(ctx, cfg, owner, repo, ...) (*git.Repository, worktreeDir, error)` that clones into `filepath.Join(cfg.CloneDir, safe(owner), safe(repo))` using token auth.

## 5. Tool implementation pattern (identical to argocd)

Each tool file has: `const xxxDescription`, `XxxParams` (json + validate + jsonschema tags),
`XxxOutput`, `XxxTool struct { *baseTool; tool.InvokableTool }`, an
`Invoke(ctx, *XxxParams) (string, error)` method, and `NewXxxTool(ctx, Configs)` using
`utils.InferTool("github_...", desc, t.Invoke)`.

- **Read/list tools** reuse the generic `filterMapMarshal[T,O]` helper + a `Filter` RE2 param
  (via `libs/toolkit/filter`) and append embedded `listOutputGuidance`.
- **Write tools** add `DryRun bool` + `Confirmed bool` params and gate execution with
  `confirm.RequireConfirmationForAction("create"/"delete"/..., params.Confirmed)` after a
  dry-run preview — exactly like `application_create.go`.
- All errors wrapped with `emperror.dev/errors`.
- All outputs pass through a **redaction** helper that strips tokens/secrets before returning.

### Notable per-tool specifics

- `repo_clone.go` — clones to `CloneDir` subdir; returns the local path + HEAD. `DryRun`
  returns the resolved path without cloning. Never accepts a caller-supplied absolute path.
- `branch_create.go` — two modes: local (create branch in an existing clone via go-git) and
  remote (create a ref via go-github `Git.CreateRef`); param `remote bool`.
- `release_create.go` — `Repositories.CreateRelease` (+ optional tag). Handles GHES upload URL.
- `pr_suggest_change.go` — posts a review comment containing a GitHub ```suggestion``` block
  on specific file+line (the "propose code fix").
- `pr_review.go` — `PullRequests.CreateReview` with event `APPROVE|REQUEST_CHANGES|COMMENT`
  and optional inline comments.
- `pr_request_reviewers.go` — `PullRequests.RequestReviewers` to assign reviewers (complements
  the item #13 prompt).
- `webhook_upsert.go` / `repo_settings_update.go` — `Repositories.CreateHook`/`EditHook` and
  `Repositories.Edit`; **validate webhook target URL to prevent SSRF** (block internal/loopback
  hosts, require https), and redact secrets in output.
- `repo_search.go` — `Search.Repositories` with query + pagination cap.
- `org_repo_list.go` — `Repositories.ListByOrg` with pagination cap.

## 6. Security controls (mandatory per AGENTS.md / CONTRIBUTING.md)

- **Path safety:** clone target is always under `Config.CloneDir`; sanitize `owner/repo`
  segments; reject `..`, absolute paths, symlink escapes.
- **SSRF:** webhook/config URLs validated — require `https`, block `localhost`, `127.0.0.0/8`,
  `::1`, RFC1918, link-local, and metadata IPs (`169.254.169.254`).
- **Secret redaction:** a `redact()` helper scrubs the token and any `secret` fields from all
  tool JSON output.
- **Timeouts:** every API call bounded by `Config.Timeout`; git clone bounded by `ctx`.
- **Confirmation gating:** all write tools require `Confirmed=true` (or `DryRun`), consistent
  with the existing `confirm` helper and the safety middleware.
- **Pagination caps:** list/search tools cap total items to avoid resource exhaustion.

## 8. Tests (`*_test.go`)

- testify **suite** pattern (`GitHubToolTestSuite`) like `argocd/suite_test.go`.
- GitHub API tools tested against `go-github-mock` (or a local `httptest` mux) — **no live
  GitHub**. Each tool: `Info(ctx)` OK → `InvokableRun(ctx, json)` → assert output; plus an
  unknown-instance error case; plus a `filter`/pagination case for list tools; plus a
  `DryRun`/missing-`Confirmed` case for write tools.
- git tools tested by creating a **local bare repo** in a temp dir and cloning from a
  `file://` URL — fully offline, deterministic.
- SSRF/redaction unit tests: assert blocked webhook hosts error out and tokens never appear
  in output.

## 11. Item #13 — PR-reviewer prompt (`components/prompt`)

This is a new persona in the **existing** prompt package, following its exact pattern
(`troubleshoot.go` + `prompts/troubleshoot.md`). No new package.

Changes in `components/prompt`:

1. `prompt.go`:
   - Add `KindPullRequestReview Kind = "pull_request_review"` to the `Kind` const block.
   - Add `//go:embed prompts/pull_request_review.md` → `var basePullRequestReview string`.
2. New file `pull_request_review.go`:
   ```go
   package prompt

   // NewPullRequestReview returns a pull-request reviewer persona prompt.
   // projectRules holds the project's custom rules and may be empty.
   func NewPullRequestReview(projectRules string, opts ...Option) *Prompt {
       return newPrompt(KindPullRequestReview, basePullRequestReview, projectRules, opts...)
   }
   ```
3. New embedded prompt `prompts/pull_request_review.md` — a reviewer persona that:
   - States the role: expert code reviewer for GitHub pull requests.
   - **Input contract:** the user must provide either a **PR link**
     (`https://github.com/<org>/<repo>/pull/<number>`) **or** the **repository name + PR
     number**; the prompt tells the agent to parse the link into `owner/repo/number`.
   - Workflow: fetch PR metadata + changed files/diff (read-only tools first), assess
     correctness, style, tests, security; distinguish verified vs inferred; cite files/lines.
   - Output: a structured review with a recommendation (`APPROVE` / `REQUEST_CHANGES` /
     `COMMENT`), optionally posting inline ```suggestion``` blocks via the GitHub tools —
     only after confirmation, consistent with the write-tool gating.
4. Tests: extend `prompt_test.go` to cover `NewPullRequestReview` (kind, base text present,
   project-rules section appended) — mirrors existing table entries.
5. README: add a row/section for the new prompt kind.

> This prompt is designed to be paired with the GitHub tools from Sections 1–11
> (especially `github_pr_get`, `github_pr_review`, `github_pr_suggest_change`,
> `github_pr_request_reviewers`), but the prompt package itself stays tool-agnostic and
> adds no new dependency.
