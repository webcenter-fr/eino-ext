# Plan: `components/prompt` — base de prompts système par type, extensible par projet

## Objectif

Créer un package Go `components/prompt` exposant une base de prompts système
solides, inspirés des prompts de kilocode (rôle + guidelines courtes et
actionnables + contraintes), avec **un constructeur par type**. Chaque
constructeur prend en paramètre les **règles custom du projet** et renvoie le
prompt assemblé (base + section projet), utilisable comme message system eino.

Types demandés :
- `Question` — orienté Q&A / analyse, read-only.
- `Troubleshoot` — troubleshooting d'infrastructure couplé à l'analyse de code
  (debug du comportement d'une app / d'un pod).
- `Check` — vérification de l'état courant d'une application ou d'un socle.
- `Architecture` — état de l'architecture (diagrammes Mermaid technique /
  fonctionnel / sécurité, infos techniques, versions, URLs).

## Référence kilocode (source du style)

Patterns repris (fichiers dans `/projects/kilocode`) :
- `packages/opencode/src/agent/prompt/{ask,debug,explore,scout,orchestrator}.txt`
  → prompts courts : **rôle** + **Guidelines** en puces actionnables + contraintes.
- `packages/kilo-vscode/src/legacy-migration/native-mode-defaults.ts`
  → `roleDefinition` / `whenToUse` / `customInstructions` pour `ask`, `debug`,
  `architect`, `review`.
- Détails clés à reprendre :
  - Ask : read-only, réponses exhaustives, Mermaid quand utile, ne pas
    implémenter sauf demande explicite.
  - Debug : réfléchir à 5-7 sources possibles → 1-2 plus probables → ajouter
    logs/diagnostics pour valider → confirmer le diagnostic avant de corriger →
    fixes minimaux et ciblés.
  - Architect : Mermaid pour clarifier l'architecture (éviter `"`, `()` dans les
    `[]` Mermaid pour ne pas casser le parsing).
  - Règles projet : « ces instructions spécifiques priment sur les instructions
    générales en cas de conflit ».

## Conventions repo (CONTRIBUTING.md) à respecter

- Prompts en Markdown sous `prompts/`, un prompt par fichier `.md`, embarqués
  via `//go:embed` (pas de gros littéraux multi-lignes en `.go`).
- Template statique embarqué ; parties dynamiques assemblées en Go (ne pas
  concaténer de nombreux petits fragments embarqués).
- `emperror.dev/errors` pour le wrapping d'erreurs ; `fmt.Sprintf` plutôt que `+`.
- Tests à côté de l'implémentation + `README.md` par composant.
- Validation finale : `go build ./... && go vet ./... && go test ./...`.
- Module : `github.com/webcenter-fr/eino-ext`.

## Design de l'API

Package `prompt` dans `components/prompt`.

```go
// Prompt est un prompt système assemblé d'un type donné.
type Prompt struct {
    kind     Kind
    base     string   // texte de base embarqué (rôle + guidelines)
    project  string   // règles spécifiques au projet (peut être vide)
    sections []section // sections additionnelles optionnelles
}

type Kind string
const (
    KindQuestion     Kind = "question"
    KindTroubleshoot Kind = "troubleshoot"
    KindCheck        Kind = "check"
    KindArchitecture Kind = "architecture"
)

// Option configure un Prompt.
type Option func(*Prompt)

// WithExtraSection ajoute une section nommée additionnelle (titre + corps).
func WithExtraSection(title, body string) Option

// Un constructeur par type. projectRules = prompt custom propre au projet
// (peut être "" si aucune règle projet).
func NewQuestion(projectRules string, opts ...Option) *Prompt
func NewTroubleshoot(projectRules string, opts ...Option) *Prompt
func NewCheck(projectRules string, opts ...Option) *Prompt
func NewArchitecture(projectRules string, opts ...Option) *Prompt

// Rendu.
func (p *Prompt) String() string            // prompt système assemblé
func (p *Prompt) Message() *schema.Message  // schema.SystemMessage(p.String())
func (p *Prompt) Kind() Kind
```

Assemblage (`String()`), dans l'ordre :
1. Base embarquée du type (rôle + guidelines).
2. Sections additionnelles `WithExtraSection` (le cas échéant).
3. Si `projectRules != ""` : section délimitée
   `## Project-specific rules` + note « ces règles priment sur les directives
   générales en cas de conflit » + le contenu de `projectRules`.

Pas de `Config`/validator nécessaire (entrées = strings) ; garder l'API simple.
Erreurs improbables → constructeurs renvoient `*Prompt` directement (pas
d'`error`) ; valider seulement `kind` en interne.

## Contenu des prompts de base (`prompts/*.md`)

### question.md
- Rôle : assistant technique read-only orienté questions/analyse.
- Guidelines : réponses exhaustives + exemples ; analyser code et concepts sans
  modifier ; commandes read-only autorisées (ls, cat, grep, git log/diff) ;
  ne PAS modifier de fichiers ni exécuter de code ; Mermaid quand ça clarifie ;
  si une implémentation est requise, suggérer de changer d'agent.

### troubleshoot.md
- Rôle : expert troubleshooting infrastructure + analyse de code pour
  diagnostiquer le comportement d'une application / d'un pod.
- Guidelines :
  - Réfléchir à 5-7 causes possibles, distiller à 1-2 plus probables.
  - Collecter des preuves read-only : logs, événements, état des ressources
    (ex. `kubectl describe pod`, `kubectl logs`, statut, métriques), config,
    et **analyse du code** concerné.
  - Valider les hypothèses par des diagnostics avant toute correction.
  - Demander confirmation du diagnostic avant de proposer un fix ; fixes
    minimaux et ciblés.
  - Distinguer ce qui est vérifié de ce qui est inféré ; citer fichiers/refs.

### check.md
- Rôle : agent de vérification de l'état courant d'une application ou d'un socle.
- Guidelines :
  - Inspecter l'état réel (ressources, santé, readiness, versions déployées,
    config) en read-only.
  - Produire un **rapport structuré** : statut global (OK / Dégradé / KO),
    tableau par composant (état, version, observations), anomalies détectées,
    actions recommandées.
  - Ne pas modifier l'état ; signaler explicitement les zones non vérifiables.

### architecture.md
- Rôle : architecte produisant l'état de l'architecture d'une app / d'un socle.
- Guidelines / format de sortie :
  - Diagrammes **Mermaid** : architecture technique, fonctionnelle, sécurité
    (flux/zones de confiance). Éviter `"` et `()` à l'intérieur des `[]` Mermaid.
  - Inventaire technique : composants, **versions**, **URLs** (endpoints,
    consoles, dashboards), dépendances, intégrations.
  - Sections : Vue d'ensemble, Composants & versions, Diagrammes (technique /
    fonctionnel / sécurité), Flux de données, Points d'attention sécurité.
  - Read-only ; baser les diagrammes sur des preuves (code/config), marquer les
    hypothèses.

## Section règles projet (commune)

Bloc ajouté par `String()` quand `projectRules` non vide, ex. :
```
## Project-specific rules

The following rules are specific to this project and supersede the general
guidelines above in case of conflict:

<contenu projectRules>
```

## Tests (`prompt_test.go`)

- Chaque constructeur renvoie un `String()` non vide contenant un marqueur du
  rôle attendu et le bon `Kind()`.
- `projectRules` non vide → section `## Project-specific rules` + contenu présent.
- `projectRules` vide → pas de section projet.
- `WithExtraSection` → titre et corps présents, dans l'ordre attendu.
- `Message()` → rôle system et contenu == `String()`.

## README.md

- But du package, liste des 4 types et quand les utiliser (`whenToUse`).
- Exemple : `prompt.NewTroubleshoot(projectRules, prompt.WithExtraSection(...)).Message()`
  injecté comme message system dans un graphe eino.

## Décisions actées

- Livrable : **package Go** (pas agents Kilo ni fichiers portables).
- API : **un constructeur par type** prenant le prompt custom projet en paramètre.
- Prompts embarqués en Markdown via `//go:embed` (convention repo).

## Hors périmètre

- Pas d'exécution réelle de LLM ni d'intégration de modèle.
- Pas de logique d'auto-détection d'infra (kubectl, etc.) : les prompts guident
  l'agent, ils n'exécutent rien eux-mêmes.

## Note d'exécution

Ce plan nécessite la création de fichiers source Go : basculer vers un agent
capable d'éditer le code pour l'implémenter.
